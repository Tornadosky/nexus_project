# PandaPickCube RGB camera probe — videos

Generated by `nexus_continuous/scripts/panda_pickcam_video.py` (companion to
`panda_pickcam_probe.py`, which produced the stills one level up). Rendered on
`mlsp2`, RTX 2080 Ti, MJWarp software path.

> **There is NO trained PandaPickCube pixel policy.** Everything in
> `rollout_SCRIPTED_*` / `grayscale_vs_colour_*` is driven by a **scripted
> open-loop joint trajectory** — a `home -> pickup` keyframe ramp, a per-episode
> sinusoidal base-yaw sweep, and a timed gripper close. It never looks at the
> cube. Every frame carries the caption
> `SCRIPTED OPEN-LOOP TRAJECTORY - NOT A LEARNED POLICY`. Do not present these as
> a learned result.

## Files

| file | what it shows |
|---|---|
| `rollout_SCRIPTED_redghost.mp4` / `.gif` | 5 episodes. LEFT = the 64x64 actor camera view, NEAREST-upscaled to 256 (so you see the *true* pixel budget, not a smoothed version). RIGHT = an independent 256x256 render for human readability. Overlay: episode + seed, timestep, live box (x, y, z) in metres. Ghost is the **upstream red** `mocap_target` — **two identical red boxes** are on screen and the actor cannot tell which is the cube. |
| `rollout_SCRIPTED_greenghost.mp4` / `.gif` | Same rollout, same seeds, `--ghost-rgba "0 0.9 0.25 1"`. The mocap target is now green, so cube (red) and target (green) are unambiguous. |
| `rollout_SCRIPTED_*_still.png` | Single frame (t = 82) from each, for slides. |

The MJWarp rasteriser **ignores geom alpha**, so the upstream `rgba="1 0 0 0.2"`
mocap target renders as a fully opaque box in the *same* red as the cube. It is
also *bigger* on screen than the cube (32.4 px vs 15.2 px at 64x64, because it
floats at z 0.23–0.43 and so is nearer the camera). Recolouring is the fix.

## Grayscale finding (measured on real rendered frames, 5 episodes, home pose)

Masks come from the same ablation recipe the probe uses (render with the mocap
target teleported away, then with the box teleported away too; diff, gated on
chroma). "Surround" is a 2 px dilated ring around the mask.

| quantity | colour (mean abs RGB) | grayscale `mean(rgb,-1)` |
|---|---|---|
| **cube vs surround** | **110.1 / 255** (max channel 169.2) | **3.75 / 255** (2.64 / 255 from pooled means) |
| red ghost vs surround | 104.4 / 255 | 3.71 / 255 |
| green ghost vs surround | 69.7 / 255 | 12.52 / 255 |

Measured means: cube RGB (220.5, 1.7, 1.7) → gray **74.6**; surrounding floor/mat
RGB (51.3, 65.6, 99.0) → gray **72.0**. The red cube and the blue-grey mat sit at
almost exactly the same luminance with opposite hue, so the channel average
cancels the signal: **contrast collapses ~29x, from 110/255 to 3.8/255.** The
cube would be near-invisible to the current pipeline. The prediction that
motivated this check was 2.6/255 and is confirmed — 2.64/255 on pooled means,
3.75/255 as the mean of the per-episode absolute differences (per-episode:
1.4, 3.6, 7.2, 2.8, 3.9).

Alternative 1-D projections of the same frames (cube vs surround, /255):

| projection | contrast |
|---|---|
| `mean(rgb)` — **what production uses** | 3.75 |
| ITU-R 601 luma `0.299R + 0.587G + 0.114B` | 3.03 — **even worse** |
| red channel only | 169.2 |
| R − B | 266.5 |
| green channel only | 64.0 |

So this is not a fixable weighting choice: the standard luma weighting is worse
than the naive average. **Panda pixels must stay in colour** (or at minimum use
the red channel / an R−B opponent channel). Note that switching the ghost to
green also fixes *its* grayscale visibility (3.7 → 12.5 / 255) and gives it a
strong green-channel signature (123 / 255), which is a second, independent reason
to prefer the green target.

Caveat on the `end_of_scripted_rollout` block in the JSON: the cube's grayscale
contrast there reads 10.9/255, but that is an artefact of one episode (seed 5,
35.2/255) in which the white arm has moved adjacent to the cube so the surround
ring is full of bright shell pixels. The pooled-mean figure for that phase is
3.15/255, consistent with the home pose.

## 3. Bonus: a video of an actually TRAINED pixel actor

`trained_pixel_actor_cartpole_aux_nesy_seed0/`

Rolled out from the saved checkpoint `runs/abl_cartpole_aux_nesy.pkl` — the
in-loop pixel-RL run **CartpoleBalance, `configs/cartpole_balance_nesy_rgb_aux.yaml`,
meta `nesy`, seed 0, 250 updates, 128 envs** (the best of the saved checkpoints:
upright fraction 1.000). No retraining; `rgb_inloop_visualize.py --load-policy`.
The rollout reproduced the checkpoint's benchmark exactly — 0.098 reward/step vs
the ablation log's `intact: 0.0985 +/- 0.0002`, upright 1.000.

* `TRAINED_inloop.mp4` / `.gif` — 250 steps of the 64x64 pixel stack the actor
  actually consumes, upscaled to 256, annotated with the active skill.
* `TRAINED_observation_filmstrip.png`, `TRAINED_skill_timeline.png`.

This is a **CartpoleBalance** policy, not a Panda policy. Equivalent videos for
the other seeds/envs (cheetah, walker, hopper; nesy / aux / neural; seeds 0–2)
already exist under `results/rgb/ablation/*/viz/rollout_inloop.mp4` and were not
regenerated.

## Reproduce

```bash
ssh mlsp2 && cd ~/nexus_project/nexus_continuous_control && source .venv/bin/activate
MUJOCO_GL=egl python -m nexus_continuous.scripts.panda_pickcam_video \
    --out results/rgb/panda_probe/video --tag redghost
MUJOCO_GL=egl python -m nexus_continuous.scripts.panda_pickcam_video \
    --out results/rgb/panda_probe/video --ghost-rgba "0 0.9 0.25 1" --tag greenghost
```

Two gotchas inherited from `panda_pickcam_probe.py` and still load-bearing:
hold a strong reference to the `RenderContext` (else `refit_bvh` raises
`KeyError`), and call `mjx.forward` on reset data before rendering (reset data is
pre-kinematics, so every frame would otherwise be identical).
