0. THE ANSWER, IN A FEW SENTENCES
================================================================================

We gave the NEXUS skill actors a camera IN ADDITION to the state vector they
already read, held everything else fixed, and compared against a state-only
control at an identical environment-step budget.

The answer is ENVIRONMENT-DEPENDENT, and it is not a wash.

  * WalkerWalk    the camera HELPED.  +7.2% training return, 3 of 3 seeds,
                  seed ranges do not overlap (Welch p = 0.054, d = +2.98,
                  paired-by-seed p = 0.047). At a 30-episode deterministic
                  eval, +14.4%, also non-overlapping. This is the one
                  environment where the actor demonstrably learned to use its
                  camera.

  * CheetahRun    the camera COST a little.  About 1-3% of training return
                  depending on the averaging window, 0 of 3 seeds better at
                  the reported window, and no measurable difference at all at
                  evaluation (-0.2%, p = 0.97). The actor never learned to use
                  the camera.

  * CartpoleBalance  the camera DESTABILISED training.  Not a lower ceiling:
                  one seed finished at 0.9999 upright fraction, the other two
                  collapsed late in training and were scored after the
                  collapse. The actor never learned to use the camera here
                  either.

The split tracks one thing: whether the actor learned to use the camera at
all. Where it did, performance improved. Where it did not, the camera was dead
weight -- neutral on cheetah, actively harmful on cartpole.

Confidence: LOW-TO-MODERATE, and bounded by n = 3 seeds per arm. Walker's
primary result does not clear p < 0.05 on an unpaired test, and with 3 vs 3 a
permutation test cannot go below p = 0.10 no matter how large the effect is.
Read section 6 before quoting anything here.

Only the `nesy` meta-policy variant was tested. This is an OPTIONAL extension,
not one of the core deliverables.

2. THE EXPERIMENT
================================================================================

--------------------------------------------------------------------------------
2.1  The algorithm and the two arms
--------------------------------------------------------------------------------

Algorithm      hierarchical PQN
               nexus_continuous/algorithms/hierarchical_ac_pqn_playground.py

Meta-policy    `nesy` (neuro-symbolic) in BOTH arms. The extension does not
               touch it. META_POLICY_TYPE: nesy in all six configs.

Arm A, the baseline -- "state_matched"
               skill_actor_k(state)              -> action
               No camera pathway exists in the actor. The environment still
               renders (see 2.2); the actor simply never receives the image.

Arm B, the extension -- "state_plus_rgb"
               skill_actor_k(pixels, state)      -> action
               A CNN encodes the image to a 128-d latent, and that latent is
               CONCATENATED to the full state vector. The state is never
               replaced. `RGB_PROPRIO: full` is what makes this true, and the
               concatenation is one line:

                   nexus_continuous/vision.py:91
                       x = jnp.concatenate([z, proprioception], axis=-1)

In both arms:
               skill_critic_k(state, action)     -> Q_k        (privileged)
               meta-policy(state / symbols)      -> skill k    (privileged)
               symbolic masks and skill rewards                (privileged)

This is the standard asymmetric / privileged-critic design (Pinto et al. 2017,
"Asymmetric Actor Critic for Image-Based Robot Learning"). Critics are used
only at training time, so privileged input to them costs nothing at
deployment, and keeping the meta-policy on state means NEXUS's interpretable
layer is unchanged and the comparison isolates the skill actors.

THE TWO ARMS DIFFER IN EXACTLY ONE CONFIG KEY:

               RGB_ACTOR: false   ->   RGB_ACTOR: true

Both config files are machine-generated from a single per-environment base by
`tools/gen_state_plus_rgb_configs.py`, which resolves both YAMLs and ASSERTS
that the set of differing keys is exactly {RGB_ACTOR} before writing. The
generated files carry a "DO NOT EDIT BY HAND" header. A `diff` of any pair
today returns the RGB_ACTOR line plus one descriptive comment line and nothing
else. This was checked again while writing this report, for all three pairs.

--------------------------------------------------------------------------------
2.2  Why BOTH arms keep USE_RGB: true -- this is the point of the design
--------------------------------------------------------------------------------

The obvious baseline -- "just turn the camera off" -- is not a baseline. In
MuJoCo Playground, `vision` is not a rendering switch, it is a TASK switch.

Verified in the installed package,
`.venv/.../mujoco_playground/_src/dm_control_suite/cartpole.py`:

    default_config():        ctrl_dt = 0.01,  episode_length = 1000
    Balance.__init__, if self._vision:
                             self._config.ctrl_dt        = 0.02
                             self._config.episode_length = 250
                             self._get_reward = self._dense_vision_reward
                                                (vs _dense_reward)

and the termination rule branches on `self._vision` as well. Separately, our
own vec wrapper feeds the actor `qpos + qvel` in vision mode but the DM-suite
featurised observation otherwise, and for WalkerWalk / CheetahRun the adapter
swaps in our ported vision subclasses
(`nexus_continuous/envs/dm_control_vision.py`) which run the MJWarp render
path at impl="warp".

So a `USE_RGB: false` control would have differed in the reward function, the
control timestep, the episode length, the termination rule, the physics
backend AND the state representation. It would have compared two different
TASKS and attributed the difference to the camera.

`RGB_ACTOR` exists precisely to separate "the ENVIRONMENT renders" from "the
ACTOR consumes". With `USE_RGB: true` + `RGB_ACTOR: false` the environment,
reward, ctrl_dt, horizon, done rule, physics backend and privileged state
vector are bit-for-bit the same as in the extension arm, and the only
difference is that the skill actors are plain state MLPs with no camera
pathway. That is the control this campaign uses.

The cost of this choice, stated plainly: the baseline arm pays the rendering
cost without using the image, so it is a fair CONTROL but not a
throughput-optimal state-only run. It is also not comparable to state-only
numbers from elsewhere in the project, which used the non-vision task.

--------------------------------------------------------------------------------
2.3  What "RGB" actually is
--------------------------------------------------------------------------------

64 x 64 GRAYSCALE, 3 stacked frames.

"RGB" is a misnomer used throughout this project, inherited from the config
flag name. There is no colour anywhere. The three channels of the actor's
input tensor are three consecutive grayscale frames, which is how velocity
reaches the actor.

Verified at `nexus_continuous/envs/dm_control_vision.py`:6 and :29
(`cam_res=(64, 64)`, `use_textures=False`, `use_shadows=False`, single active
tracking camera per env).

Encoder (`nexus_continuous/vision.py`, class RGBEncoder), DrQ-v2 convention:

    input   64 x 64 x 3   (3 stacked grayscale frames as channels)
    Conv 32, 3x3, stride 2, SAME  + ReLU     ->  32 x 32 x 32
    Conv 64, 3x3, stride 2, SAME  + ReLU     ->  16 x 16 x 64
    Conv 64, 3x3, stride 2, SAME  + ReLU     ->   8 x  8 x 64
    flatten -> Dense 128 -> LayerNorm -> tanh    ->  128-d latent, in [-1, 1]

    RGB_EMBED_DIM: 128
    RGB_AUGMENT: true, RGB_AUG_PAD: 4   (DrQ random-shift, actor update only)
    RGB_SHARED_ENCODER is OFF, so every skill actor carries its OWN CNN.

--------------------------------------------------------------------------------
2.4  Scale, budget, and what the runs are
--------------------------------------------------------------------------------

    3 environments   CartpoleBalance, WalkerWalk, CheetahRun
    x 2 arms         state_matched, state_plus_rgb
    x 3 seeds        0, 1, 2
    = 18 runs

    Budget, identical for every run:
        250 updates x 128 parallel envs x 64 steps = 2,048,000 env steps

    Skills per environment (unchanged by the extension):
        cartpole  3   recover_balance, center_cart, damp_motion
        walker    4   stand_recover, walk_forward, stabilize_gait,
                      energy_efficient
        cheetah   3   accelerate_forward, stabilize_posture,
                      energy_efficient_run

    State vector in vision mode is qpos + qvel:
        cartpole   2 + 2  =  4-d
        walker     9 + 9  = 18-d
        cheetah    9 + 9  = 18-d

    Hardware: one shared RTX 2080 Ti (TU student pool), jax 0.11 CUDA,
    mujoco 3.11 + mujoco-warp 3.11. NUM_ENVS is pinned at 128 because 256 OOMs
    the in-loop renderer on 11 GB; both arms use it, so it cannot confound.

CROSS-ENVIRONMENT COMPARABILITY WARNING. Cartpole's base config carries
NUM_MINIBATCHES: 8 where walker and cheetah use 64, so at the same
environment-step budget cartpole takes 8x FEWER gradient steps. This is
IDENTICAL in both cartpole arms, so it cannot confound the state-vs-state+RGB
contrast. It does mean cartpole's absolute numbers must not be compared across
environments. It is also relevant to the interpretation in section 5.

--------------------------------------------------------------------------------
2.5  What the extension costs
--------------------------------------------------------------------------------

Parameters added per skill actor, counted from the module definition:

    Conv 32       3*3*3*32   +  32  =        896
    Conv 64       3*3*32*64  +  64  =     18,496
    Conv 64       3*3*64*64  +  64  =     36,928
    Dense 128     4096*128   + 128  =    524,416
    LayerNorm                       =        256
                                      ----------
    encoder subtotal                     580,992
    wider first MLP layer  128*256  =     32,768
                                      ----------
    per skill actor                      613,760   (~0.61M)

Because the encoder is not shared, the total added parameters are that times
the number of skills:

    cartpole   3 skills  ->  ~1.84M
    walker     4 skills  ->  ~2.46M
    cheetah    3 skills  ->  ~1.84M

Input dimensionality of a skill actor:

    cartpole      4-d  ->  132-d    (97% of the actor's inputs are pixel-derived)
    walker       18-d  ->  146-d    (88%)
    cheetah      18-d  ->  146-d    (88%)

WALL-CLOCK: NOT MEASURED, AND NOT CLAIMED HERE. No training run.log or result
JSON in this campaign records elapsed time, so this report does not put a
number on the training-time cost of the extension. The one timing that IS
committed is for EVALUATION, in `results/rgb/state_plus_rgb_eval30/README.md`:
scoring all 18 arms at 30 episodes took about 2h50m, with state+RGB arms at
~15 min each and state-only arms at ~2-4 min each. That ratio is confounded --
state+RGB arms score six ablation conditions and state-only arms score only
`intact` -- so it is not a clean per-step cost either. If the training-time
cost matters to a decision, it needs to be measured; the qualitative statement
"the extension is substantially more expensive per environment step" is safe,
a specific multiplier is not.


================================================================================
3. METRICS
================================================================================

PRIMARY -- training return.
    `training_curves.json -> curves.episode_return`, the mean of the LAST 20 of
    250 updates. Each update is already a mean over 128 parallel envs, so this
    is by far the highest-resolution number the campaign produced. It carries
    exploration noise and is not a deterministic score.

SECONDARY -- deterministic evaluation of the FINAL weights.
    `pixel_ablation.json -> results.intact`. Reported at BOTH 5 and 30
    episodes, because the episode count changed what the metric could resolve
    (section 6.3). No checkpoint selection of any kind: whatever the run
    finished with is what gets scored.

    The metric key is environment-specific and both arms of an environment use
    the same one:
        cartpole   upright_fraction_mean   (fraction of the 250 steps upright)
        walker     reward_per_step_mean
        cheetah    reward_per_step_mean

CAMERA-USE PROBE 1 -- corruption ablation, at evaluation.
    Corrupt ONLY the skill actor's image and re-score. Conditions:
        frozen_first    every frame replaced by the t=0 frame
        random_replay   frames from an unrelated real rollout
        shuffle_frames  the 3 frames of the current stack permuted
        zeros           blank image
        const_action    actor replaced by its own per-skill mean action
    The meta-policy and critics always see the real state, so a drop is
    attributable to the actor's pixel pathway.

CAMERA-USE PROBE 2 -- in-training pixel sensitivity.
    `curves.pixel_sensitivity`, computed inside the actor loss with no
    gradient (hierarchical_ac_pqn_playground.py, "blindness monitor"): the
    minibatch's images are rolled by one so each state is paired with a
    DIFFERENT real frame, and the probe reports

        mean |a(real pixels) - a(other real pixels)| / (action range)

    A blind encoder scores ~0. This uses no corruption at all, so it is an
    independent second opinion on the ablation.

STATISTICS.
    All spreads are the SAMPLE standard deviation, ddof = 1, across the 3
    seeds. At n = 3 the population convention (numpy's default) understates
    the spread by sqrt(3/2) = 1.22x, so the convention matters and is stated
    in every table below.
    Welch p is the two-sided unequal-variance t-test. "paired" is a paired
    t-test over the three seed-matched pairs. Cohen's d uses the pooled s.d.
    Post-hoc power is reported only to show what a metric COULD have detected,
    never as evidence about a hypothesis.

--------------------------------------------------------------------------------
4.2  WalkerWalk -- the camera helped, and the result is robust to the one
     analysis choice that could have manufactured it
--------------------------------------------------------------------------------

+7.2% on the primary metric: 189.51 +/- 1.80 -> 203.20 +/- 6.25. All three
seeds improved. The seed ranges do not overlap: the worst state+RGB seed
(196.48) is above the best state-only seed (191.54). Welch p = 0.054,
Cohen's d = +2.98, paired-by-seed p = 0.047, paired 95% CI [+0.45, +26.92].

Choosing an end-of-training averaging window is a researcher degree of
freedom, so it was swept. Walker survives it at every window from 5 to 50
updates -- 3/3 seeds and non-overlapping ranges throughout:

     window   state only   state+RGB    delta    Welch p   seeds   overlap
        5      188.96      204.32      +8.13%    0.026      3/3      no
       10      189.11      203.81      +7.77%    0.030      3/3      no
       20      189.51      203.20      +7.22%    0.054      3/3      no   <- reported
       30      189.62      202.06      +6.56%    0.059      3/3      no
       50      187.41      199.07      +6.22%    0.085      3/3      no
      100      177.45      188.56      +6.27%    0.408      2/3      yes
      250      121.69      133.41      +9.63%    0.319      2/3      yes

The reported window of 20 sits in the MIDDLE of the surviving range, not at its
favourable end -- windows of 5 and 10 give a larger effect and a smaller p.
The 100- and 250-update rows are averages over the learning phase, not
end-of-training scores; they still favour the extension but no longer separate
the seeds, which is what averaging over the noisy early curve should do.

At 30-episode evaluation, +14.4% with non-overlapping seed ranges (0.6151 /
0.7581 / 0.7658 against 0.8010 / 0.8338 / 0.8123). Note that the extension arm
is also far TIGHTER across seeds at eval (s.d. 0.0167 vs 0.0849) -- the
baseline's seed 0 has one collapsed evaluation episode and the extension's does
not. That episode is NOT excluded from anything: evaluation reset keys are
PRNGKey(9000 + 97*episode + seed), a function of (episode, seed) and not of the
arm, so both arms start every episode from the same initial state. Baseline
seed 0 episode 4 and extension seed 0 episode 4 are the same initial state; the
baseline fell over and the extension did not. That is a paired outcome, not
contamination, and dropping it would erase most of the effect under test.

--------------------------------------------------------------------------------
4.3  CartpoleBalance -- a STABILITY finding, not a lower ceiling
--------------------------------------------------------------------------------

The headline -32% is dominated by two late training collapses and one seed
that was scored three updates into its own collapse. Reading it as "the camera
makes cartpole worse at balancing" is wrong. Per seed:

  seed 1  Never collapsed. Finished at 24.42 training return and 0.9999
          upright fraction over 30 episodes. That is parity with the
          state-only baseline to within a single non-upright step in 7,500.

  seed 0  Sat at ~24.5 for 240 updates, then fell apart in the FINAL THREE:
              ... 24.58  24.54  24.50  24.47  24.42 | 22.23  15.19  9.95
          Its maximum, 24.88, was at update 210. The last-20 window therefore
          straddles the cliff and reads 23.28; the final weights, which are
          what evaluation scores, are the ones at 9.95. 30-episode upright
          fraction 0.7193.

  seed 2  Peaked at 23.34 at update 148, then decayed monotonically over about
          ten updates (22.55, 21.19, 19.53, 16.01, 10.72, 7.26, 4.21, 2.73,
          1.75, 0.67) and stayed at approximately zero for the remaining 100
          updates. Last-20 mean 0.91. 30-episode upright fraction 0.2551.

Instability is not exclusive to the extension arm. State-only seed 0 also dipped
late, to 13.81 at update 201 -- but it recovered monotonically to 23.4 by the
end and evaluated at a perfect 1.000. The difference between the arms is
recovery, not the absence of turbulence.

Two consequences for how the cartpole row should be read:

  1. Evaluation scores FINAL weights with no checkpoint selection. Under a
     "best checkpoint" protocol the cartpole story would look very different --
     seed 0 would score near 1.0. Nothing here is evidence about the achievable
     ceiling; it is evidence about end-of-training stability at this budget.

  2. The stored analysis flags cartpole's 30-episode comparison as
     "non-overlapping". Do not quote that. It is degenerate: the state-only arm
     is exactly 1.0 on all three seeds (zero variance, at the metric's ceiling)
     and the best extension seed is 0.9999. The ranges are formally disjoint by
     one part in ten thousand. That is a ceiling artifact, not a separation.

The direction is stable and the magnitude is small, of order 1-3%:

     window   state only   state+RGB    delta    Welch p   seeds better
        5      121.46      119.83      -1.33%    0.527       1/3
       10      121.43      119.80      -1.34%    0.482       1/3

The cost is negative at all seven windows and the Welch p ranges from 0.086 to

1.4-1.7), and it does not survive the window sweep. The honest summary is a
small real cost, not a null and not a significant one.

At evaluation there is nothing at all: +0.9% at 5 episodes (p = 0.88), -0.2% at
30 episodes (p = 0.97), 50 of 90 paired episodes won. Both metrics at both
episode counts agree.

DO NOT QUOTE `const_action` FOR THESE RUNS. Replacing the actor with a constant
per-skill action is not a pixel-specific control for an actor that also reads
the state -- it removes the actor's entire input, state included. It is
retained in the JSONs as a sanity check that the actor matters at all, and it
is hatched out in fig2 for exactly this reason.

A NOTE ON THE STORED VERDICT FIELD. `pixel_ablation.json -> actor_uses_pixels`
reads `false` for every walker seed. Ignore it. It thresholds the MEDIAN of
{frozen_first, random_replay, zeros} at 30%, a bar calibrated on
`RGB_PROPRIO: none` actors whose ONLY input is the camera. An actor that also
holds the state can ride it through a corrupted frame, so the median under-reads
and hides disagreement between conditions. The ablation script itself prints a
WARN to this effect on every `RGB_PROPRIO: full` run. The per-condition table
above is the thing to read.


================================================================================
5. INTERPRETATION
================================================================================

Everything in this section is INTERPRETATION. The measurements are in section
4; this is the story that fits them, and it is not the only story that could.

--------------------------------------------------------------------------------
5.1  The answer to "might achieve better performance" is conditional
--------------------------------------------------------------------------------

The extension helped on exactly the environment where the actor learned to use
its camera, and did not help on the two where it did not. The correlation is
perfect across the three environments we ran, which is a sample of three, and
the direction is at least mechanically sensible: an input the network has
learned to read can carry information, and an input it has not learned to read
cannot.

What that does NOT establish is causation. fig3 plots camera dependence against
performance for the nine extension runs and the association is visible, but
with three environments and three seeds each it is an association, not a
demonstration that learning to see is what produced walker's +7%.

--------------------------------------------------------------------------------
5.2  A mechanism, offered as a hypothesis
--------------------------------------------------------------------------------

On these three environments the state vector is small (4 to 18 numbers), exact,
and complete: qpos + qvel fully determines the physical configuration. A 64x64
grayscale render of that same configuration is a LOSSY RE-ENCODING of
information the actor already has, in a form that is far more expensive to
read.

So the image adds no information, and it costs:
  * ~0.61M parameters per skill actor (1.8M-2.5M per run) whose only gradient
    is the deterministic policy gradient through the privileged critic;
  * 128 additional input dimensions to the first MLP layer which, carrying no
    new signal, must be SUPPRESSED rather than exploited -- on cartpole that
    is 128 of the actor's 132 inputs;
  * substantially more compute per environment step (not quantified here,
    see 2.5).

Under this reading, the null-to-negative results on cartpole and cheetah are
the expected outcome and walker's positive result is the one that needs
explaining. Two candidate explanations for walker, neither tested: the camera
provides a genuinely useful redundant view for a contact-rich task where small
state errors compound, or the extra pathway acts as a regulariser / an
additional gradient route that helps at this particular (short) budget. The
52.4M-step follow-up (section 6.4) was launched specifically to discriminate
between them, because a regularisation effect should wash out at a long budget
and a genuine perceptual benefit should not.

--------------------------------------------------------------------------------
5.3  Why cartpole is hurt most -- consistent with, not shown to be, an
     optimisation burden
--------------------------------------------------------------------------------

Cartpole is the environment where the ratio of nuisance to useful input
dimensions is worst (128 pixel dimensions to 4 state dimensions), AND the
environment that takes 8x FEWER gradient steps than the others at the same
environment-step budget (NUM_MINIBATCHES 8 vs 64). If the cost of the extension
is "the optimiser has to learn to ignore a large, useless input", then the
environment with the largest such input and the fewest optimisation steps to
do it in is exactly where you would expect it to bite hardest, and exactly
where you would expect late-training instability rather than a lower plateau.

That is a coherent account and it matches what the curves look like. It is not
a demonstration. With n = 3 -- one clean seed, one that collapsed at update
247 and one at update 150 -- the data cannot separate an optimisation-burden
explanation from seed luck. Testing it properly means either raising cartpole's
NUM_MINIBATCHES to 64 and re-running both arms, or running many more seeds.
Neither was done.

--------------------------------------------------------------------------------
5.4  What walker's corruption pattern does and does NOT support
--------------------------------------------------------------------------------

Look again at the walker rows in 4.5. One condition replicates and the others
do not:

    frozen_first   +0.721  +0.622  +0.723    reliable, fatal, all three seeds
    random_replay  +0.059  +0.408  +0.102    erratic, one seed dominates
    zeros          +0.138  +0.533  +0.379    erratic, same seed dominates
    shuffle_frames -0.013  +0.019  +0.014    consistently nothing

`frozen_first` holds the image at the t = 0 frame: the picture is a perfectly
valid, correctly rendered scene, it just stops CHANGING. That is the condition
that reliably destroys performance on every seed.

`random_replay` (real frames from an unrelated rollout -- moving, but wrong)
and `zeros` (a blank image -- neither moving nor a scene) are erratic across
seeds. `shuffle_frames` (the same three frames in a scrambled order -- pose
preserved, temporal order destroyed) costs nothing on any seed.

What replicates is therefore DEPENDENCE ON THE IMAGE CHANGING, not dependence
on the image being CORRECT, and not dependence on frame ORDER.

We do not claim the actor decodes its pose from pixels. A representation that
is driven by frame-to-frame variation, does not care whether that variation is
the true scene, and does not care about the ordering within the stack, is
consistent with the encoder supplying something more like a
motion / activity / state-change signal than a reconstruction of the walker's
configuration. Distinguishing those would need a decoding probe -- regress
qpos+qvel from the frozen latent and report held-out R^2 -- which was not run.

--------------------------------------------------------------------------------
5.5  A side observation: the state vector may suppress perception
--------------------------------------------------------------------------------

fig8 asks whether handing the actor a cheap, exact channel stops it learning
the expensive one. On cheetah the contrast is clean and the effect is large:
the pixels-only arm at the SAME budget reaches an in-training pixel sensitivity
of 0.414, and adding the state vector collapses it to 0.0011 -- a factor of
374. Both arms derive from the same base config and differ only in the actor's
proprio width, so this is a one-key contrast.

It does not generalise cleanly, and section 7 flags this on the figure. On
cartpole and walker the surviving pixels-only references are NOT one-key
contrasts -- they also carry an auxiliary pixel->state loss and a longer
meta-decision interval -- so their ratios (15.0x and 3.7x) mix several changes.
More pointedly, walker's own one-key pixels-only run (single seed) has a pixel
sensitivity of 0.075, which is LOWER than the 0.098-0.117 of walker's
state+RGB arm. On walker, adding the state vector did not suppress perception;
it coincided with more of it.

So: strong on cheetah, one environment, one key. Treat "a cheaper channel stops
perception being learned" as a hypothesis this campaign supports in one place
and contradicts in another.


================================================================================
6. CAVEATS -- READ THESE WITH THE RESULTS, NOT AFTER THEM
================================================================================

--------------------------------------------------------------------------------
6.1  n = 3. This is the binding constraint on everything above.
--------------------------------------------------------------------------------

Walker's primary result gives Welch p = 0.054. That does not clear 0.05.

It is worth being precise about what "not significant" means at this sample
size. With 3 versus 3 observations there are C(6,3) = 20 possible group
assignments, so an unpaired permutation test CANNOT return a two-sided p below
2/20 = 0.10, no matter how large the effect is. Likewise a seed-level sign test
cannot go below 0.25. Walker's unpaired permutation p is exactly 0.10, the
floor. Its sign test is exactly 0.25, the floor. Both are pinned by the design,
not by the data.

So "not significant at 0.05" here is a statement about how many seeds we ran,
not about how weak the effect is. The effect size is large (d = +2.98) and the
seed ranges are disjoint on the primary metric.

Seeds needed per arm for 80% power at the OBSERVED effect size:

    primary metric (train return)      n = 4    (one more seed than we have)
    30-episode eval                    n = 7
    5-episode eval                     n = 17

That is what it would take to settle it. It is cheap on the primary metric and
expensive on the eval metric, which is itself the point of 6.3.

Post-hoc power is quoted here for one purpose only -- to compare what each
metric could have resolved -- and is not evidence about any hypothesis.

--------------------------------------------------------------------------------
6.2  Only the `nesy` meta-policy was tested
--------------------------------------------------------------------------------

Every run in this campaign uses META_POLICY_TYPE: nesy. The NEXUS paper
evaluates three meta-policy variants -- neural, symbolic and nesy -- and its
own recommendation is the PURELY SYMBOLIC one.

The extension changes only the skill actors, and the skill actors are identical
across all three variants; the meta-policy sits above them and selects between
them. So the extension SHOULD transfer in principle. That is an architectural
argument, not a measurement. It was not verified, and the paper's recommended
variant is specifically the one we did not test.

If this extension were to be taken further, running the symbolic variant is the
first thing to do, not the last.

--------------------------------------------------------------------------------
6.3  A metric lesson worth recording
--------------------------------------------------------------------------------

This campaign was first written up with a 5-episode deterministic evaluation as
its headline. On that metric walker showed "no effect": seed ranges overlapping,
Welch p = 0.31.

The SAME frozen policies were then re-scored at 30 episodes. Nothing was
retrained -- the 18 pickled policies were re-loaded and re-rolled with
`--episodes 30`, same environment, same rollout code, same metric keys, same
250-step episodes, same reset keys. The only change is how many episodes score
each condition.

    walker, eval metric        5 episodes        30 episodes
    state only                 0.7138 +/- 0.0921  0.7130 +/- 0.0849
    state + RGB                0.7855 +/- 0.0438  0.8157 +/- 0.0167
    difference                 +10.0%             +14.4%
    seed ranges                OVERLAP            DO NOT OVERLAP
    Welch p                    0.31               0.17
    achieved power             0.16               0.35
    paired episodes won        11 / 15            76 / 90

The 5-episode metric had an achieved power of 0.16 against the effect actually
present. It was never going to resolve this. The metrics never disagreed about
the world; one of them simply could not see the difference and reported that
absence as a null.

The general lesson: at these effect sizes, "we measured it and found nothing"
is only informative if the measurement could have found something. Both episode
counts are reported side by side in fig5 and in the tables in section 4 so that
this is visible rather than buried, and both trees remain on disk.

--------------------------------------------------------------------------------
6.4  The full-budget walker run is not in here
--------------------------------------------------------------------------------

`tools/run_walker_full_campaign.sh` runs WalkerWalk at 6400 updates x 128 envs
x 64 steps = 52,428,800 environment steps, 25.6x this campaign's budget, both
arms, to test whether walker's +7% survives a long run or is an
optimisation-time artefact. It was IN PROGRESS when this report was written.
Nothing from it is included, and no result here should be read as anticipating
it. Its outputs will land in `results/rgb/state_plus_rgb_full/`, which does not
yet exist; the committed 2.05M tree is never written to.

--------------------------------------------------------------------------------
6.5  `const_action` is not a meaningful condition here
--------------------------------------------------------------------------------

Repeated from 4.5 because it is the easiest number in the JSONs to misquote:
for a `RGB_PROPRIO: full` actor, replacing the actor with a constant per-skill
action removes the STATE as well as the image. Its large drops (0.95-0.999 on
walker and cheetah) say the actor matters; they say nothing about the camera.
Do not quote it as evidence of pixel dependence.

--------------------------------------------------------------------------------
6.6  Scope limits worth stating once
--------------------------------------------------------------------------------

  * Three environments, all dm_control_suite, all with small exact state
    vectors. Nothing here speaks to a task where the state vector is
    incomplete or where the camera carries information the state does not --
    which is the case the extension is ultimately FOR.
  * One camera, one resolution, one encoder architecture, one frame-stack
    depth. No sweep.
  * One budget (plus the pending 52.4M walker run). Walker's advantage at
    2.05M steps is 4% of the paper's budget.
  * Grayscale, not colour.
  * Final weights only, no checkpoint selection -- which matters most for
    cartpole (4.3).

8. WHAT WAS REMOVED FROM THIS REPORT, AND WHY
================================================================================

Earlier versions of this document reported three campaigns. Two of them --
offline distillation of state skills into pixel policies, and in-loop pixel RL
with `RGB_PROPRIO: none` -- have been removed, and their artifact trees were
deleted from the working tree (they remain in git history at 8333c39 and
earlier).

The reason is that they answered a different question. Both replaced the state
vector with pixels, so they tested whether a skill actor CAN act from images.
That is a real question and the answer was broadly yes, but it is not the
question the supervisor's brief asked, which is whether ADDING vision buys
anything. Neither had a matched-budget state-only control, so neither could
have answered it: a pixels-only arm has nothing to be better or worse THAN.

Their numbers are therefore not reported here as findings, and nothing in
section 4 or 5 depends on them. A small number of scalars from those runs
survive as REFERENCE LINES only -- the pixels-only sensitivity levels in fig2,
fig4, fig6, fig7 and fig8, and the table in 5.5. Those scalars live in
`results/rgb/state_plus_rgb/reference_baselines.json`, which records their
provenance, their budget (identical, 2.048M steps), and explicitly which of
them are one-key contrasts and which are not. No claim in this report rests on
a number from a deleted file.

Two housekeeping notes for whoever touches this next. `results/rgb/README.md`
still links to the deleted `ablation/`, `inloop/` and `distill/` trees and
still leads with their headline tables; and both it and
`results/rgb/state_plus_rgb/figures/README.md` still attribute the RGB
suggestion to the NEXUS paper rather than to the supervisor's brief (section
1). Neither was edited as part of this report.

    configs/cartpole_balance_nesy_state_matched.yaml

    python tools/gen_state_plus_rgb_configs.py

(`<env>:<arm>:<seed>`):

    tools/run_state_plus_rgb_campaign.sh cartpole:state_matched:0 \
        cartpole:state_plus_rgb:0 walker:state_matched:0 ...

    tools/run_state_plus_rgb_eval30.sh walker:state_plus_rgb:0 ...

    python tools/analyze_state_plus_rgb.py            # -> corrected_analysis.json
    python tools/analyze_state_plus_rgb.py --readme   # -> figures/README.md
    python tools/plot_state_plus_rgb_figures.py --figure all

JSONs and records the source path of every input under `runs[*].sources`. It
does not modify any existing result JSON.

mujoco-warp 3.11, in-loop rendering via MJWarp (CUDA). The headless-rendering
setup is in the top-level README.

10. VERIFICATION NOTE
================================================================================

Every quantity in sections 4 and 5 was recomputed from the raw per-run JSONs
while this report was written -- last-20 means from `training_curves.json`,
intact scores and ablation drops from both `pixel_ablation.json` trees, and the
Welch / paired / window-sweep statistics from scratch. All of them reproduce
the values stored in `corrected_analysis.json` to the digits quoted.

Three points where an earlier phrasing was tightened rather than reproduced:

  1. "Roughly 4 more seeds would settle the primary metric." The correct
     reading of the power calculation is n = 4 PER ARM for 80% power at the
     observed effect -- that is ONE more seed than we have, not four more. The
     corresponding figures are 7 per arm for the 30-episode eval and 17 per arm
     for the 5-episode eval. Section 6.1 states it this way.

  2. Cheetah's "p = 0.086 to 0.53" is the range of the WELCH p across the seven
     windows of the sweep, and is correct as such. It omits the strongest
     cheetah statistic, the paired-by-seed p = 0.029 at the reported window,
     which is reported in 4.4 alongside the reason not to lean on it.

  3. Cartpole's 30-episode comparison is stored with `seed_ranges_overlap =
     false`. It is a ceiling artifact (1.0000 exactly, three times, against a
     best of 0.9999) and 4.3 says so rather than quoting the flag.

One claim in the earlier draft could NOT be verified and has been removed
rather than restated: the "roughly 10x wall-clock" cost of the extension. No
committed run.log or result JSON in this campaign records training wall-clock
time. Section 2.5 says what is actually on disk and what is not.
